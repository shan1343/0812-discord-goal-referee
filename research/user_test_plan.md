# 사용자 검증 계획 — D

목적: 사용자가 설명 없이도 배정 이유를 이해하고, 틀린 배정을 고치며, 진행률의 근거를 찾을 수 있는지 검증한다.

## 운영 원칙

- 참가자 3명은 개발에 직접 관여하지 않은 사람을 우선한다.
- 가명 P1/P2/P3만 기록하고 이름·전화번호·학교 ID는 수집하지 않는다.
- 테스트 전 화면 녹화/캡처 여부와 기록 목적에 동의를 받는다.
- 진행자는 정답이나 클릭 위치를 먼저 알려주지 않는다. 30초 이상 막히면 힌트를 주고 `도움 후 성공`으로 기록한다.
- 성공 여부는 관찰 행동으로 판정하며, 만족도만으로 성공 처리하지 않는다.
- 현재 Kakao UI에서는 실행하지 않는다. Discord v3 빌드와 HTTPS URL이 준비된 뒤 시작한다.

## 시작 문구

“이 테스트는 사용자가 아니라 제품을 평가합니다. 막히거나 틀려도 괜찮습니다. 화면을 보며 생각나는 것을 말해 주세요. 가짜 프로젝트 데이터만 사용하며, 녹화·캡처에 동의하지 않으면 메모만 남기겠습니다.”

## 공통 시나리오와 질문

### 과제 1 — 배정 이유 이해

상황: `/seed_demo happy_path`와 `/assign` 실행 결과가 열린 상태.

진행자 질문:

1. TASK-001 담당자가 누구라고 이해했나요?
2. 왜 그 사람에게 제안됐는지 화면에서 근거를 찾아 말해 주세요.
3. AI가 확정한 것인가요, 사람이 아직 확인해야 하나요?

성공 기준: 60초 안에 owner, reason, 원문 evidence를 찾고 `제안/확정` 상태를 정확히 구분한다.

### 과제 2 — 틀린 배정 수정

상황: 담당자의 일정 충돌이 새로 드러났다고 가정.

진행자 질문:

1. “민재는 14시에 수업이라 14시 마감 작업을 맡을 수 없다”를 반영해 배정을 바꿔 주세요.
2. 무엇이 바뀌었고 왜 바뀌었는지 확인해 주세요.
3. 수정 결과를 최종 확정하려면 무엇을 해야 하나요?

성공 기준: 90초 안에 제약 입력→reassign→변경 이유 확인을 수행하고, Confirm 전에는 확정되지 않았음을 설명한다.

### 과제 3 — 진행률 근거 찾기

상황: 누군가 “완료했다”고 말했지만 필수 파일이나 테스트가 빠진 상태.

진행자 질문:

1. 해당 Task가 100%가 아닌 이유를 찾아 주세요.
2. 누락된 파일과 최신 파일 버전을 찾아 주세요.
3. 다음에 누가 무엇을 해야 하는지 말해 주세요.

성공 기준: 90초 안에 `/progress`와 `/files` 또는 웹 대시보드에서 state, 누락 evidence, 최신본/checksum, next_action을 찾는다.

## 종료 질문

- 가장 이해하기 어려웠던 표현이나 화면은 무엇이었나요?
- 실수로 확정하거나 재배정할 것 같았던 지점이 있었나요?
- 이 도구를 실제 팀에서 쓴다면 가장 먼저 확인할 정보는 무엇인가요?
- 1~5점: 배정 이유 이해 / 수정 용이성 / 진행률 신뢰도

## 판정 지표

- 무도움 과제 성공률 = 무도움 성공 과제 수 / 9
- 참가자 완주율 = 세 과제를 모두 무도움 또는 도움 후 성공한 참가자 수 / 3
- 배정 수정 시간 = 과제 2 시작부터 변경 이유 확인까지
- 근거 찾기 성공률 = 과제 1·3의 근거 항목 성공 수 / 6
- 심각도: P0 데모 중단·보안 위험, P1 핵심 과제 실패, P2 지연/혼동, P3 문구 개선

## 증거 저장 규칙

- 원본: `evidence/user-tests/P1/`처럼 참가자별 폴더
- 필수: 동의 여부, 시작/종료 시각, 결과표, 주요 캡처 또는 녹화 링크
- 개인정보가 보이는 캡처는 제출 폴더에 넣지 않는다.
- GitHub Issue가 생성되면 결과표의 Issue 열에 실제 URL을 기록한다.
